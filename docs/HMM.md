## HMM 小額實盤（2026-09-13，第 9 次 informed override）—— **單一市場、每所 $50**

**使用者決定（原話）**：「**好**」——回應的是一則把這條 override 授權什麼、
紀律寫死哪幾條、以及「先 `--record-only` 跑一輪再開 live」逐條列出的訊息。
所以它授權的是**到 record-only 為止的全部動作 ＋ 這一節本身**；
**翻成 live 的那一下要再說一次**（本節末尾那條紀律）。

同一天使用者把這條線命名為 **HMM（對沖做市）**，見 §HMM 那一節。

**這條 override 推翻的是什麼（誠實版）**

不是「策略 #2/#3 不得進 executor」——套利是第 4 線，定位是「只錄不做」。
真正被推翻的是**我們自己在 TODO §1.40 寫下的 Gate 0**，三天前才凍結：

| 關 | 狀態 |
|---|---|
| G1 每 ticker 每天 ≥ 10 筆 | **8/9 過，但過的是宇宙的補集** —— 成交帶錄前 80 名（價差緊），20–60 bps 的毛邊際全在看不見的 57 個長尾裡 |
| G2 逆選擇 markout > −毛邊際 | **沒量。** backtest-audit 第 13 項的陷阱（逆選擇最低的往往是 API 壞掉的）也沒查 |
| G3 集中度 | 量了：最大 1 個 30% / 前 5 個 93% / 前 10 個 100% -> **那是 5 個機會不是 8 個** |
| G4 cost=0 對照 | 沒做 |
| G5 用判決那台機器跑 bootstrap SE | 沒做 |

§1.40 自己寫的下一步是「放寬成交帶宇宙，7 天後重跑 G1」，而這條 override
要在那 7 天到期之前先上線。**這是一次知情的推翻，推翻的是自己三天前的判準。**

**為什麼仍然值得做，而理由不是「我覺得會賺」**

這次要買的東西**統計上買不到**，跟第 7 次 override 同一個論證：

| 問題 | 誰能回答 |
|---|---|
| 長尾流量夠不夠（G1） | 成交帶，而且只能等。實盤在這題上**嚴格更差** |
| **我們掛進去之後簿口長什麼樣** | **只有實盤。** §1.40 自己把它標成「未量測 1」，而它**沒有任何離線儀器量得到**（backtest-audit 第 16 項，博弈動態） |
| 掛 20–60 bps 打到我們的是什麼流 | 只有實盤（G2 的分子要我們自己的成交） |
| 兩腿延遲、對帳、HALT 在真實延遲下撐不撐得住 | 只有實盤（X4 的 M4 / M5） |

**第二列是這條 override 的全部理由。** 它不是「提前驗證」，是一個離線量不到
的量，而 §1.40 已經把它標成推論不是量測。

**為什麼代價比第 7 次低**

| | 第 7 次（2026-09-08，SDV） | **本次（HMM）** |
|---|---|---|
| 帳戶 | Bitget，**與 V7 共用**（被手動單爆過兩次） | **Lighter ＋ HL 獨立帳戶**，不碰 OKX/Bitget 體系 |
| 金額 | $300–500 | **每所 $50**（X4 §0 凍結值；實際 HL $98.30 / Lighter $88.78） |
| 下單層 | 產品端新寫 | **既有的 B3 掛單路徑**（2026-09-04），已審過、今天彩排過 |
| 方向暴露 | 有（單邊持倉） | **兩腿對沖**，設計上沒有方向 |
| 帳戶層風控 | 無 | **B6**：逐帳戶曝險上限 ＋ 剩餘抵押品下限，讀交易所回報，超了 HALT |
| 市場數 | — | **1 個** |

**寫死、事後不放寬的紀律**

* **損益不得作為 edge 證據。** Gate 0 的 G1/G2/G5 判決只認計分器的輸出，
  不吃這批實盤損益（§0.92 判掉 C/D 變體的同一種錯）。
* **唯一要看的四個判準**，全部是 X4 的既有條目，不新發明：
  M2 掛單成交率 ≥30%（<10% 這條路關掉）／M3 成交後 60 秒中價漂移 > −1 bps／
  M4 兩腿延遲中位 <2s、p95 <10s／M5 一腿行情延遲 >10 秒時引擎必須 **HALT
  而不是補單**。
* **市場數 = 1。** 理由是**第一次送真單**，不是缺帳戶級風控（那個今天做好了）。
  而且它**寫進設定裡**：`max_account_gross_usd: 70` 在第二個 live 行程一上來
  就會讓 `account_budget.py` 的 B3 變紅（Σ 逐腿上限 120 > 70）。
  加第二個市場 = 要改那個數字 = 要重新想一次，那個摩擦是刻意的。
* **標的在跑之前就凍結**：`arb/engine/config_HMM_GMX.yaml`，GMX，已 commit。
  不得因為看到別的配對更好看而中途換（§0.92 的同一種錯）。
* **不得退回 Standard 費率層**省那 0.40 bps —— Standard 的 60 req/min
  結構上做不了做市。
* **翻成 live 要使用者再說一次。** 「好」授權到 record-only 為止；
  第一次真的送單是另一個動作。
* 要放大金額或市場數，另開一次 override。

**代價自負（使用者知情後選擇的）**

* **第一次送單就是真錢**，而掛單路徑的 `unknown` 狀態（撤單超時）在真實網路
  上從未發生過。
* **資金費沒算進毛邊際**。兩腿都是永續，持有過結算點就付／收
  （實測 entropy 1.0000 / hedge 0.9600 bps per 8h，方向未分析）。
* **提款費／gas 沒算**，要有可成交量才攤得出來。
* **未成交的放棄邊際沒算** —— §1.28 量到被動執行要付 7.27 bps，
  那是在 Binance 厚標的上量的，這裡未知。
* **簿口更新率**：record-only 實測 Lighter GMX 的簿口**九秒沒動過**，
  而 HL 是 0.3 秒。markout 的視窗必須長於它（§1.41 的 AI +57 教訓），
  M3 的 60 秒視窗是照這個選的。
* 緩解：每所 $50、單市場、兩腿對沖、`max_position_usd` $60/腿、
  B6 的兩道帳戶級閘門、M5 的 HALT 不可關。

**上線前實測到的現場數字（2026-09-13 record-only，一個快照不是判決）**

    HL GMX       7.7203/7.7214   半價差  0.71 bps   簿口年齡 0.3 秒
    Lighter GMX  7.6412/7.7921   半價差 97.78 bps   簿口年齡 9.5 秒

掃描器 13.6 天量到的 Lighter 中位是 33.48 bps，所以**此刻比中位寬三倍**。
一個快照不構成任何結論，但它的方向與整條線的前提一致：
**掛單那一側的價差是結構性的寬，不是暫時的錯價。**

### HMM（對沖做市）—— 第 4 線上線構造的正式名稱（2026-09-13 使用者命名）

**使用者從三個選項裡選了「HMM（對沖做市）」**（Hedged Market Making），
而他選的不是最短的那個，也不是最省事的那個 —— 是**最準的**那個。

    掛單腿   在不流動的場館掛 post-only（Lighter，maker 0.40 bps 全場最低）
    對沖腿   成交後立刻吃單對沖到流動的場館（HL core，taker 4.50 bps）
    賺什麼   不流動那一側**結構性的寬價差**，不是兩所之間的錯價

**為什麼不叫「套利」，這一段是名字的全部重點**：這條線**沒有收斂交易**。
兩所的中價可以完全一樣，它照樣賺錢。而「套利」這個詞會把**等收斂**的心智
模型帶進來 —— 那正是 §0.75 與 §1.39 死掉的地方（帶會回去，而你在轉帳
到達前就被吃掉）。CLAUDE.md 有一整條 mistake 記著
「**被推翻的結論會以「詞」的形式活下來**」，所以這裡刻意不沿用。

`small-trader-alpha-1` 自己的說法就是這個：他把機會分兩類，中價套利
（兩腿吃單）他說「太容易套」，而**價差套利他叫 the favorite**，並且點明
它就是**帶跨場館對沖的做市**。我們過去一年做的全是他不推薦的那一類。

**HMM 與另外兩個容易混淆的東西的分界**：

| | 構造 | 場館 | 在哪 |
|---|---|---|---|
| **HMM** | 掛單 ＋ **跨場館吃單對沖** | Lighter × HL | TODO §1.40 / §1.41，`../arb` 引擎 |
| 倉位型做市（§1.29） | **單場館**掛單，庫存用上限管，不對沖 | 只有 Lighter | 引擎**跑不動**（maker 模式一定對沖），要另開單場館模式 |
| §0.75 家族 | 兩腿都吃單，等帶收斂 | 多所 | **已結案 NO-GO**，扣費就負 |

**名字的適用範圍**：HMM 指的是**這個構造**，不是整條第 4 線。第 4 線
（兩場館套利）是容器，HMM 是它上面第一個要碰真錢的東西。

### shadow 模式退場（2026-09-14 使用者決定）—— **只跑實盤**

使用者原話：「Shadow 不要跑了現在只跑實盤」「不然 shadow 一直佔流量」。

**理由是雙重的，而且兩邊都是當天量出來的：**

1. **它結構上量不到它該量的東西。** shadow 的 `shadow_decisions` 與
   `quotes_cancelled` 逐筆相等，而 `quotes_rested` **恆為 0** ——
   `maker_rested` 需要交易所回一個 OPEN 狀態，而 shadow 從不送單。
   所以 **M2 的分母永遠是零、M3 沒有成交可記、M4 沒有真實往返**：
   決定這條線行不行的三個判準，在那裡結構上量不到。
   當天的證據：GMX 跑了十小時乾淨的 shadow，而 live **起不來**
   （`hyperliquid-python-sdk` 沒裝）。「shadow 很乾淨」對
   「live 跑不跑得起來」零資訊量。

2. **而它同時是共用 IP 的主要消耗者。** `_http_keepalive_loop` 只在
   `not record_only` 時起 —— 所以 shadow 每 10 秒打兩腿、record-only 不打。
   七支 shadow = 84 req/分，實測後果是**每十分鐘八支引擎一起被擋 60 秒**，
   而被擋的是**重連**，那時會下單的那支手上有部位。
   一個什麼都量不到的模式，佔著會下單那支需要的頻寬。

**連帶改掉的三處**：`make_hmm_config.py` 產的 .bat 不再帶 `--shadow`；
`hmm_screen` 的 G2 從 `shadow.csv` 改讀 live 的 `maker.csv`（同一個問題，
換成真的發生過的事回答）；`http_keepalive_sec` 10 -> 50 秒
（連線池上限 75 秒，原本每 10 秒是需要的 7.5 倍）。

**`--record-only` 不受影響**：它不跑策略、不報價、不起 keepalive，是
§0.75 錄製家族的資料來源（九支，餵 `minutes.csv`）。要停的是 `--shadow`。

**一般化的那一條**（已寫進 mistake.md 2026-09-14）：**一個「彩排模式」的
價值，等於它跟正式演出共用的路徑有多長；而它跳過的每一段，就是它結構上
看不見的每一段。** 所以要列的是「shadow 不做哪些事」那張清單。

命名紀律照 [[feedback_plain_language]] 與 SDV 的先例：這是**使用者定的詞**，
所以可用；**我不得再自行發明別的簡稱**（不要出現「HMM-A」「HMM+」這種我
自創的變體名，要新名字先問）。
