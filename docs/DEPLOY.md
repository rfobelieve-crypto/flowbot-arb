# 部署架構：引擎在 AWS 東京，儀表板在 Vercel（2026-09-04 決定）

> 使用者原話：「儀表板可以放到 vercel，但系統主體放 aws 上最好」「這樣應該會最快」。
> 這份文件把那個決定寫死，並把它**不可以順便改掉的東西**一起寫下來。
>
> 這取代 `LIVE_50U_SPEC.md` §4 裡「儀表板放 Railway → jarvis」那條路徑。
> **§4 的其餘內容（唯讀、零按鈕、公開面只出百分比方向時間）全部不變。**

---

## 一、為什麼是這個組合（兩個都不是隨便選的）

**引擎在 AWS 東京（ap-northeast-1）**——這不是新決定，是既有量測的結論：

- `LIVE_50U_SPEC` §3 實測本機到各場館往返：Lighter 32 ms、RH 65、Binance 65、
  HL 80、Bitget 88、OKX 95。**沒有任何 Railway 區同時靠近兩條腿。**
- 同份規格 §6 引用 entropy-arb 作者自己的建議：**伺服器建議東京 AWS**。
- 真正吃延遲的是**撤單**（掛單被吃之前撤掉），那是 M3 逆選擇成本本身。
  現在引擎已經在量它（`entropy_arb/metrics.py` 的 `cancel` p50/p95/p99），
  所以搬過去之後**有數字可以對照，不是憑感覺**。

**儀表板在 Vercel**——它是純前端 + 唯讀 API，沒有長駐迴圈、沒有金鑰、
掛掉不影響交易。Vercel 的部署盲區（1–2 分鐘）對它無所謂，因為它不交易。
**這正是為什麼交易迴圈不能放在那裡**（`CLAUDE.md` §3）。

---

## 二、資料流：單向，而且是引擎「推」出去

```
        AWS 東京 EC2                              Vercel
  ┌────────────────────────┐              ┌──────────────────┐
  │ engine（唯一有金鑰的地方）│  HTTPS 推送   │ 唯讀儀表板        │
  │  + 錄價器               │ ───────────► │ 零按鈕            │
  │  + 控制通道（TG/命令檔） │   出站 only   │ 沒有任何金鑰      │
  └────────────────────────┘              └──────────────────┘
            ▲
            │ TG / SSH（人 → 引擎，四個動詞）
            人
```

**三條不可以破的規則：**

1. **只有出站。Vercel 永遠不主動連進引擎主機。** 引擎是金鑰所在的地方；
   給它開一個入站埠，就是給金鑰開一個入站埠。儀表板要的是狀態快照，
   而快照可以用推的。
2. **金鑰不進 Vercel。** `CLAUDE.md` §1 寫死。Vercel 那邊最多有一個
   「接收快照」的共享祕密，那個祕密外洩的後果是「有人可以偽造儀表板數字」，
   不是「有人可以下單」。**這兩件事的等級差三個數量級。**
3. **控制通道不經過儀表板。** 四個動詞走 TG／落地命令檔，儀表板掛掉時仍然
   要能用（`LIVE_50U_SPEC` §6 的原話）。

---

## 三、最快的那條路（推薦），以及它的取捨

**引擎每 30 秒 POST 一份 JSON 快照到 Vercel 的一個端點，Vercel 存進 KV，
頁面讀 KV。**

```
engine ──POST /api/ingest（Bearer <共享祕密>）──► Vercel KV ──► 頁面
```

- **為什麼最快**：引擎端只多一個出站 HTTP 呼叫，不用 IAM、不用 VPC、
  不用開任何埠。Vercel 端兩個檔案（一個 ingest route、一個頁面）。
- **取捨**：那個端點在公網上、而且**接受寫入**。所以它必須
  （a）驗 Bearer token，（b）只寫顯示狀態、永遠不回傳指令給引擎，
  （c）拒絕過大的 body。**引擎不讀那個端點的回應內容**——它只看 HTTP 狀態碼。
  這一條要寫進程式碼的註解裡，否則哪天有人會想「順便讓儀表板回傳參數」。

**替代方案（更耐久但慢一點架）**：引擎用 instance role 寫 S3（已經在 AWS 上，
不用多一組憑證），Vercel 用唯讀 key 讀。適合之後要保留歷史快照時再換。

**兩份快照，不是一份**：

| 檔案 | 內容 | 誰看得到 |
|---|---|---|
| `public.json` | 百分比、方向、時間、守衛狀態（紅/綠） | 世界 |
| `private.json` | 美元權益、部位、餘額偏斜 | 只有登入的你 |

拆開的理由是公開面硬規則（`CLAUDE.md` §1 / `DASHBOARD_REF.md` §四.6）：
**絕不出現合約張數、美元權益、帳戶餘額、單筆部位金額**。一份快照裡同時
放兩種資料，遲早會有人把錯的那半渲染出去。

## 四、引擎要新增的東西（B6 的前置，還沒做）

一支 `entropy_arb/snapshot.py`，職責只有一件事：**把引擎已經在算的東西
序列化成 JSON 推出去**。不新增任何計算——這是 `LIVE_50U_SPEC` §4 的原話
（「全部是引擎已經在算的東西，不新增計算」）。

現成可以直接放進快照的（都已經存在）：

| 欄位 | 來源 |
|---|---|
| 兩腿簿口、年齡、是否過期 | `v.book` / `is_fresh()` |
| 當前溢價 bps、帶寬 | `premium_bps()` / `cfg` |
| 部位、淨差額、session MTM | `describe_positions()` / `session_pnl()` |
| 守衛狀態（HALT / 操作員暫停 / 波動熔斷 / 場館 down） | `control_status()` 已經組好了 |
| 掛單：成交率 M2、殘留的報價 | `maker_rested` / `maker_fills` / `_maker_open` |
| 延遲 p50/p95/p99（含**撤單**） | `self.lat.snapshot()` |
| 未解釋部位變動、對帳結果 | `unexplained_events` |
| 錄價器活著沒 | `recorder.rows_written` / `_recorder_dead` |

**`control_status()` 和 `lat.snapshot()` 是今天才做的，本來就是為了這個。**

它必須是**旁路**：推送失敗只記 log，永不影響交易（`CLAUDE.md` §2 的
「旁路壞掉不影響交易」）。同一個理由，它用自己的 HTTP session，
不共用下單那條連線。

## 五、順序（不要跳）

1. **先有 AWS 東京主機**（A4，卡在使用者）——沒有它，儀表板顯示的是
   一台會睡眠的 Windows 桌機的狀態。
2. **再有真實資料**——`LIVE_50U_SPEC` §4 的前提是「引擎有資料之後才做 B6，
   避免空殼」。M1 之前引擎不會產生一筆成交。
3. **然後才是 snapshot.py → Vercel**。

**現在就能做的只有第 3 步的引擎側**（快照序列化 + 推送，純旁路、不碰錢）。
要不要提前做是速度與空轉的取捨：做了就能在 `--shadow` 模式下先把整條顯示
鏈路跑通，而 shadow 現在就能跑。

## 六、掃描器該放哪（2026-09-13 加，因為那天它把 live 的路擋住了）

> 本節之前這份文件只講引擎與儀表板。**掃描器沒有被指定位置**，
> 而 2026-09-13 它把 HMM 的上線路擋住了 —— 所以那是一個要回答的問題。

### 觸發這一節的事

驗收 HMM 的 record-only 那一輪，`lighter_tape` 紅了。最小測試：

    wss://mainnet.zklighter.elliot.ai/stream -> 403 Forbidden

**既有連線全部正常**（GMX 引擎的 Lighter 簿口 3.3 秒、`lighter_mid` 201/217
市場活著），**只有新連線被拒**。殺掉重啟又 403、凍在 uptime=1s。
`lighter_tape` 死了約 1.7 小時，丟掉不可回填的長尾成交帶。

量我們自己的腳印，答案很難看：

| 來源 | Lighter REST | |
|---|---|---|
| **掃描器** | **65 次/分** | 一輪去重後 196 次，`CYCLE_SEC` 當時是 180 |
| 10 支引擎 reconcile | 40 次/分 | 每支 `reconcile_sec = 15` |
| keepalive ／ 其他 | ~10 次/分 | |
| **合計** | **約 110 次/分，24 小時不停** | 外加約 12 條常駐 WS |

**掃描器一支是 live 引擎（約 4/分）的十六倍**，而擋住我們的那一層是
CloudFront/WAF —— **per-IP，而且掃描器一個憑證都不帶**，所以帳戶是不是
Premium 完全不相關。**升級分級解決不了。**

### 判準：研究負載不可以吃掉執行負載的重連預算

失效模式對兩者的嚴重度差一個等級：

* 研究錄製器連不回來 = 少一段資料，難受但活得下去。
* **live 引擎的對沖腿行情在封鎖期間斷線 = 回不來，而那時它手上有部位。**
  `_venue_down` 會在三次失敗後暫停、`max_consecutive_stale` 在有曝險時 HALT
  —— 系統會正確地停，但**停在一個看不見對沖腿的狀態**。

### 已做（2026-09-13）：掃描器 `CYCLE_SEC` 180 -> 600

65 -> 20 次/分。分析上的代價約等於零，而且是量的不是辯的：§1.39 量到這支
掃描器自己的**腿差 53 秒**，所以 180 秒的格本來就比它能分辨的細。
**唯一被改到的是 `frozen()` 那道閘門**，語意斷點寫在 `scanner.py` 的常數旁
與 `spread_arb_paired.frozen()` 的 docstring 裡。

### 引擎**不要**放 Railway（四個理由，延遲只是最小的那個）

第一節那句「沒有任何 Railway 區同時靠近兩條腿」是延遲的理由。真正擋住它的
是另外四個，而這個專案每一個都付過錢：

1. **檔案系統是暫存的。** flow_system 的 CLAUDE.md 有一整條 mistake：
   warmup buffer 存在容器裡，每次部署被重置回 git 那份，
   「暫時的偏差」變成每天重演的常態，三個月沒人發現。
   引擎寫 `minutes.csv` / `maker.csv` / `status.json`，而那些是判準的證據。
2. **`git push` 會重啟它。** Railway 推 main 就自動部署 ——
   也就是**每一個 commit 都會重啟一個持倉中的做市引擎**。
   B3 的狀態機救得回來（重啟用 `strict=True` 重讀真實部位），
   但那個窗口是真的，而**掛在交易所上的那張報價不會因為我們重啟就消失**。
3. **出口 IP 共享而且會變。** 這一點對引擎比對掃描器糟得多：
   IP 換掉或落在被節流的那個上，**引擎的 WS 重連就失敗，而那時它有部位**
   —— 正是本節要避免的那個失效。
4. **前科**：未釘版的 `mcp` 在上游發 2.0 當天炸掉 agent-mcp（跟那次 push
   的內容無關）；收緊一個 config guard 讓 OKX executor 停了 50 分鐘。

**引擎留在本機（或照第一節搬 AWS 東京）。** 它現在的 Lighter RTT 是 32 ms。

### 掃描器放 Railway：可以，而且分開不影響引擎

**查證過的事實：引擎與掃描器之間沒有任何資料耦合。**
引擎讀的只有三樣：自己的 YAML（啟動時）、`control.cmd`、自己寫的 CSV。
**它不 import `arblib`，從來沒讀過掃描器的任何輸出。**
掃描器搬走，引擎一行都不用改、一個輸入都不會變。

實際存在的耦合全部是資源層的，而且全部對引擎有利：

| | 影響 |
|---|---|
| per-IP 的 WAF 預算 | **從對等競爭變成獨佔** —— 65 次/分 的競爭者消失 |
| 本機 CPU／連線數 | 少一支每輪打 3,000 次 REST 的程式 |
| WAF 聲譽 | 掃描器的無憑證流量不再算在引擎的 IP 上 |

**不會變的兩件事**（寫下來免得有錯誤期待）：引擎的 RTT 不變（還在本機），
引擎自己的 REST 量不變（reconcile 4/分 + keepalive）。

**間接的那一條要知道**：掃描器餵 `spread_arb_paired`，而那支選出了 GMX。
所以掃描器的輸出決定**引擎交易哪個標的** —— 但那是研究時間尺度的事
（標的選一次就凍結在設定裡），不是執行期相依。

### 便宜的形狀：Railway 不存檔，本機拉

掃描器的成本問題只有一個：60 MB/日的 CSV 要落在哪。
而 Railway 的檔案系統是暫存的（見上面第 1 點）。

```
  Railway（掃描器，零金鑰）            本機（有金鑰，durable）
  只留最近 1–2 天的滾動緩衝   ◄────── 每輪拉一次（本機發起，出站 only）
                                      D 槽存全量，10 個消費者一行不用改
```

這樣暫存檔案系統**變成可接受的**：重新部署最多丟一輪，對廣度掃描無所謂。
而且它守住三條既有界線：**不開入站到有金鑰的機器**（本機主動拉）、
**Railway 上沒有任何金鑰**（掃描器本來就零憑證）、
**不碰 flow_system 的 MySQL**（arb repo 的邊界規則）。

### 順序：先測 IP，不要先蓋再測

**Railway 的出口 IP 是共享的 —— 它對 Lighter 可能已經被別的租戶打髒了。
這件事在部署之前是未知的，而它決定整個計畫成不成立。**

1. **先等 600 秒的節奏生效並觀察。** 如果 20 次/分 就不會被擋，
   這整件事不用做。這一步是免費的。
2. 還是被擋 -> 丟一支二十行的探針上 Railway，打一次 Lighter 的 REST ＋ WS，
   看回什麼。
3. 探針乾淨 -> 才做搬遷（arb repo 目前**沒有任何部署設定**，要新加）。

**不要先蓋再測。** 2026-09-13 那個 403 就是「以為可以一直打」的結果。

### 一條硬規則

搬完之後**只能有一支掃描器在跑**。兩支就是 2026-09-03 的 duplicate-scanner
bug —— 兩個掃描器打同一個公開 API，正是我們為此花掉一天的那個限流，
也正是這整條路的起點。
