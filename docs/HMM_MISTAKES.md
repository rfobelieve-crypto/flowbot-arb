## 2026-09-15: 一個把結論數字**完全不改變**的儀器錯誤 —— 逆選擇的一半是兩所基差,而它只污染歸因

**What happened:**

HMM 的每筆分解（`arb/engine/tools/fill_decomp.py`，09-14 寫的）報出:

    賺到的半價差 +13.34   逆選擇 -9.44   ->   淨 +3.67 bps
    （Quant Arb 35,107 筆:+1.25 / -1.07 / +0.19）

我據此對使用者說「**我們的半價差是他的 10.6 倍、逆選擇也是 11 倍,
收入端贏他但被逆選擇吃掉更多**」。

使用者問:「你有想過為什麼我們是他們的十倍嗎,搞不好這是我們原本當初設計的
問題」。查下去,那個十倍有一半是我的儀器:

`fill_decomp` 的成交當下中價取 CSV 的 `mid_at_fill`,而那個欄位記的是
**對沖腿（HL）**的中價（`engine.py` `taker_v.book.mid()`）,未來中價卻來自
**掛單腿（Lighter）**的逐檔錄製器。**兩所基差被算進去了。**

    修正後: 賺到的半價差 **+7.67**   逆選擇 **-4.01**   淨 **+3.67**

**而那正是這一條要記的東西：淨值一個位元都沒變。**

因為基差 b 在兩項之間**對消**:

    half_錯 = half_對 - s·b      adv_錯 = adv_對 + s·b      net 不變

所以沒有任何一個結論數字看起來不對、沒有任何自曝檢查會紅、
損益對得上、跟實盤同號 —— **它只污染歸因**。而歸因正好是使用者問的那件事,
也正好是決定「下一步要修哪裡」的那件事:
逆選擇 11 倍 -> 「這個市場太毒,要換標的」;
逆選擇 3.7 倍而價差 6.1 倍 -> 「做市腿比他好,問題全在對沖腿」。
**兩個結論的下一步完全相反。**

**Root cause（三層,第三層是新的）:**

1. **修了生產者,沒有修消費者。** 引擎在 09-14 就為了這件事新增了
   `maker_mid_at_fill`（原地註解白紙黑字寫著「差一點就直接拿 taker 的去算,
   那會把兩所的基差混進逆選擇裡」）。但那個欄位**沒有寫進 maker.csv** ——
   於是唯一的分析端只好從外部錄製器重建,而重建的第一版拿了錯的欄位。
   同族:[[2026-08-29 一份資料兩個讀者只改了一個]]。差別是這次兩個讀者
   之一是**隔天才出生的**,所以「枚舉現有讀者」擋不住它。

2. **教訓寫在 `mistake.md` 而我隔天在新檔案裡犯了它。**
   [[2026-09-07 剛用某個錯誤判掉一條線,四小時後又寫了一次]] 的第二次,
   間隔從四小時變成一天。

3. **新形狀：一個不改變任何結論數字的錯誤。**
   我們現有的守衛全部是「某個數字會變得不對」的形狀 —— 自曝檢查、
   控制配對、cost=0 對照、跨儀器對照。它們**對這一類結構性地全盲**,
   因為錯誤在兩個分量之間對消。
   能抓到它的只有一種檢查:**對分量本身的物理上限**。這次補的 C3 就是 ——
   post-only 掛在觸價或更裡面,所以**賺到的半價差不可能超過這個市場自己的
   半價差**;舊讀數 13.21 > 12.81,一跑就紅。

**Correct approach（已做）:**

* 兩端的中價都改成取自**同一本簿口**（掛單腿自己的逐檔錄製器），
  而不是「引擎記一端、錄製器記另一端」。
* 新增 C3（分量的物理上限）。舊讀數保留並列印 —— 它被引用過。
* maker.csv 補上 `maker_mid_at_fill`,下次不必重建。
* 新工具 `markout_curve.py` 的對照是**同一個市場的隨機時刻**,不是他的
  絕對值 —— 跨場館比絕對 bps 本來就沒有分辨力。
* 順手補 `tests/test_csv_shape.py`:AST 掃每個 `_append_csv`,列的格數必須
  等於表頭欄數。這週第三次加欄位,而對齊**沒有任何東西在檢查**
  （`_append_csv` 的契約是 "Never raises",所以差一格只會讓後面每一欄靜默
  平移,`pandas` 照樣給你一張看起來正常的表）。破壞注入變紅。

**Rule:** **一個錯誤不動到結論數字,不代表它沒有後果 —— 它可能只動到歸因,
而歸因決定下一步做什麼。** 凡是「A ＋ B = 結論」形式的分解,要對
**A 和 B 各自**寫一道物理上限的檢查,不可以只檢查結論。
判斷法很便宜:問「有沒有一個量,它進到 A 是正的、進到 B 是負的、大小一樣」
—— 有的話,那個量就是這個分解量不到的東西,而且它不會讓任何守衛變紅。

第二條:**一個欄位「引擎算了」不等於「分析端讀得到」。** 修一個「拿錯資料源」
的 bug 時,不只要在生產端加上對的那個量,**還要把它送到會被讀的地方** ——
否則下一個人（可能是明天的你）仍然只能從錯的那個欄位重建。

## 2026-09-14: 殺了 python 沒殺會把它拉回來的 cmd 包裝層 —— 一支「已經搬到 Railway」的掃描器多跑了 21 小時,那就是「每十分鐘斷線一次」的來源

**What happened:**

使用者從早上就一直收到 Discord 告警,而且抱怨「為什麼會一直斷線」。實盤引擎
每十分鐘被擋一次 60 秒,對沖打不出去,裸曝險衝破上限 -> HALT。

追下去,鏈子是這樣的:

    本機 tools/scanner.py 還在跑（我 9/13 說它「搬到 Railway」了）
      -> 每一輪序列打 **139 次** Lighter REST（for 迴圈 + sleep(0.06)）
        -> 429（Lighter 限流）-> 405（CloudFront WAF）-> API unreachable
          -> 對沖腿打不出去 -> 裸曝險 +184 > max_net_base 141
            -> 18:51 XPL HALT,之後一小時沒報價

**429 在 405 之前 —— 那個順序就是答案。** 429 是「你請求太多」,不是「你被封」。

而它為什麼還在跑:9/13 我把掃描器搬到 Railway 時,改的是**開機啟動檔**
（Startup 的 .bat),那只擋「下次開機不要起」。**這台機器沒重開過**,所以
9/10 07:40 起的那個 `cmd /K run_scanner.bat` 包裝層一直活著,在我殺掉 python
之後,於 **9/13 22:08 又把它拉了回來**,跑了 21 小時。

同一天同一個形狀的第二個:`run_recorder_OPENAI.bat`（一支已退場的 shadow）
從當天 08:52 起也是這樣活著的。

**Root cause:**

**這個系統有兩套獨立的重拉機制**,而它們做的是同一件事:

    .bat 自己的 `:loop` + `timeout 30` + `goto loop`      （30 秒）
    ops/arb_watchdog.ps1 比對簽章再 Start-Process           （5 分鐘）

於是「停止」變成六個動作,而其中兩個**沒有任何當下的回饋**:

    flat -> 註解看門狗那一列 -> 殺 python -> 殺 cmd 包裝層 -> 等 5 分鐘 -> 複查

殺 python 當場可見（行程清單回空,我確認過也貼給使用者看過）;另外兩個要等
「不發生」才看得見。所以「看起來停了」這個證據,剛好只覆蓋六個動作裡的一個。

最刺眼的是 `run_hmm_XPL.bat` 自己檔頭寫的四步停止程序,第 3 步是
「only then kill **the processes**」—— 複數,而**它沒有寫那個 cmd 包裝層**。
我照著它做了兩次。

**Correct approach（已做,兩個方向都反向證明過）:**

把「這支該不該跑」變成**一個檔案**,兩個重拉者都讀它:

    logs\stop\<啟動器檔名>.stop

    .bat 側    `:loop` 之後第一行 `if exist logs\stop\%~n0.stop goto end`
    看門狗側   Start-Process 之前 Test-Path,命中就記進 $stopped 不拉

停止 = 建一個檔案;恢復 = 刪掉它。**一個看得見的狀態,不是一串要記得的動作。**
21/22 支啟動器加了閘門（universe 那支真的沒有迴圈,不需要）。

反向證明（ZEC,record-only,中斷約 2 分鐘）:建檔 + 殺 python -> 包裝層自己
退出、python 維持 0;看門狗印 `10/11 alive | STOPPED by flag: ZEC` 而且沒有
拉它;刪檔 -> `RELAUNCHED: ZEC`。live 那支（XPL）另外用副作用中性化的複本
單獨驗解析:無 STOP 檔 -> 迴圈正常,有 STOP 檔 -> python 那行一次都沒跑。

順手解開一個謎:「每支錄製器有兩個包裝層」是 `cmd /K` —— 一個在跑迴圈,
另一個是 /K 跑完保留下來的閒置殼,它不會拉任何東西。

**Rule:** **「我停了它」在一個由外部排程或自動迴圈維持的系統裡,不是一個
當下可以驗證的命題。** 而更根本的一條:**兩套獨立的重啟機制 = 停止需要兩個
動作,而其中至少一個沒有回饋。** 修法不是「記得兩個都做」,是**讓它們讀同一
個狀態**。

判斷法很便宜:問「如果我現在殺掉這個行程,**有幾個東西會把它拉回來**」。
答案大於 1 就先去合併它們,再談停止程序。

## 2026-09-14: 我在 .ps1 裡加中文註解,看門狗就少看了兩個成員、scan_pull 連死 31 次 —— 而 log 印的是 "all 9 alive"

**What happened:**

查斷線時發現看門狗的 log 寫 `all 9 alive`,而註冊表裡有 **11** 個成員。
同一份 log 裡還有每 5 分鐘一次的 `scan_pull FAILED: 無法將引數繫結到
'Path' 參數,因為它是 Null`,連續 31 次。

根因是同一個:`ops/arb_watchdog.ps1` **沒有 BOM**,PowerShell 5.1 於是用主控台
碼頁（這台是 cp950）讀它。我當天稍早在裡面加了中文註解,那些 UTF-8 位元組
被 cp950 誤解之後,**把後面幾行吞掉了**。

被吞掉的是什麼,決定了後果:

    16:34 本地  `$Arb` / `$Lock` 的賦值被吞
                -> scan_pull 連 31 次失敗 -> Railway 的掃描資料完全沒拉回本機
    18:24 本地  `'XPL'` 與 `'universe'` 兩個成員被吞
                -> 看門狗只看得到 9 個

**後果最嚴重的是第二個:我 18:24 才把 XPL（那天唯一的 live 引擎）註冊進
看門狗,而看門狗從頭到尾沒看到它。** 一支會送真單的引擎,整晚沒有任何人在守,
而 log 每 5 分鐘印一次 `all 9 alive` —— **跟健康狀態長得一模一樣**。

補上 BOM 之後,三件事同時好了,還多修一個既有的潛伏 bug:第 192 行
`"$_" -like '*紅*'`（帳戶預算的紅燈偵測）在沒有 BOM 時一直是亂碼,
那個比對**從來沒有命中過**。

**Root cause:**

這跟 [[2026-09-13 .bat 的中文註解讓 cmd.exe 跳行]] 是**同一個根的 PowerShell
版本**:那次是 cmd.exe 的位元組偏移記帳被 UTF-8 打亂,這次是 PowerShell 用
cp950 解 UTF-8 把行吃掉。兩次的失效方向都是最壞的那個 —— **不報錯、不中止,
只是少做幾件事**。

而我當天稍早才剛在 mistake.md 讀過那條 .bat 的教訓,並且**在 commit 訊息裡
引用過它**。我把它讀成「.bat 的規矩」,而它是「**任何由非 UTF-8 感知的解譯器
逐位元組讀的檔案**」的規矩。

**Correct approach（已做）:**

給整個檔案補 UTF-8 BOM（前插 3 個位元組,其餘一個位元組都不動）。
選 BOM 不選「把中文改成 ASCII」,理由是前者連既有的 `'*紅*'` 那一行一起修,
而且不需要每個未來的編輯者都記得這條規矩。

驗收用的是**產物**:同一支腳本從 ParserError 變成 `all 11 alive`,
scan_pull 當場拉回 12.9 MB / 3 個檔。

**Rule:** **PowerShell 腳本要有 UTF-8 BOM,否則 PS 5.1 用主控台碼頁讀它。**
判斷法是二元的:`任何非 ASCII 位元組 ∧ 沒有 BOM` = 這支 .ps1 現在就在吞行。
`.bat` 那條（註解只能 ASCII）與這條是同一個家族,而家族的成員是
**「誰在逐位元組讀這個檔,它認不認得 UTF-8」**,不是副檔名。

第二條,關於這種故障的形狀:**「all N alive」這種摘要行,N 必須是算出來的,
而且要跟一個獨立的來源對得上。** 一個少數了兩個成員的看門狗,跟一個健康的
看門狗,印的是同一句話。凡是摘要行裡有數字的,要問「這個數字有沒有可能是
錯的,而我看不出來」。

## 2026-09-14: 兩個判準名字都像「兩側性」,量的卻是不同的東西 —— G1 從來沒有基差項,而 XPL 與 AERO 都死在那裡

**What happened:**

XPL 上線後,實盤的報價側別是 **332 : 0**（sell_entropy : buy_entropy）——
引擎從頭到尾只想報一側,庫存堆到 $58.7/$60 之後停住,十分鐘內 95 次
`blocked by position caps`。

而篩選器說它沒問題,**包括那一關本來就叫「兩側性」的 G5**:

    G5 吃單流少數側  **46.0%**   -> 流量非常兩側,過關

兩者不矛盾,因為**它們量的是不同的東西**。G5 量「誰在吃單」;而我們報哪一側
是由**基差的正負號**決定的。XPL 的 Lighter 中價持續比 HL 低約 10 bps,
於是只有一個方向清得過門檻,流量再兩側也沒用。

真正的洞在 G1。它是:

    net = lt_hs - hl_hs - fees        <- **沒有基差項**

它隱含假設兩所的中價對齊。有持續基差 b 時,真實的兩側是

    賣側 = lt_hs + b - hl_hs - fees
    買側 = lt_hs - b - hl_hs - fees

**舊 G1 算的正好是兩者的平均,而那兩側都不是。** 量出來:

    XPL   舊G1 +3.99（過關） 賣 +14.40 / 買 **-6.42**  基差 +10.41
    AERO  舊G1 +3.14（過關） 賣 +11.54 / 買 **-5.26**  基差  +8.40
    POL   舊G1 +3.27（過關） 賣  -7.29 / 買 +13.82     基差 -10.55

**篩選器當時通過的四個市場,兩側檢驗全部死。** 132 個市場改判之後 0 個通過。

連帶解開一個懸了一天的紅燈:C6（AERO 的在線時間必須 < 50%）從註冊起就一直
是 52% 左右 —— 也就是**G7 從來沒有解釋過 AERO**。當天我刻意不去調那個門檻讓
它變綠（把儀器擬合到答案正是它要擋的事）。現在知道真正的原因是基差。

**Root cause:**

**一個判準的名字描述的是它的意圖,不是它的算式。** 「兩側性」這個詞同時
指著兩件事 —— 流量的兩側、與**價格的兩側** —— 而我們只實作了前者,然後用
那個名字說服自己這一面已經蓋到了。

這跟 [[2026-08-26 被推翻的結論會以「詞」的形式活下來]] 是鄰居,但方向相反:
那次是舊結論靠一個詞活下來,這次是**一個詞讓人以為某個檢查存在**。

第二層:G1 的算式裡沒有基差項,而那不是疏忽 —— 是**兩所中價對齊**這個假設
從來沒有被寫下來過。沒寫下來的假設不會被檢查。

**Correct approach（已做）:**

`hmm_universe.py` 的 G1 改判 `net_min = lt_hs - |基差| - hl_hs - fees`,
基差用兩所中價的 60 秒桶對齊算中位（都是它已經在讀的來源,不引進第三份資料;
樣本 < 30 桶的標成**未量**,不猜）。舊的單側 `net` 仍然算出來並印在「舊G1」欄
—— 它被引用過,不可以悄悄消失,而兩欄擺在一起本身就是這個改動的證據。

自曝檢查裡**關鍵的是 C8**:

    C7 XPL 的買側必須 < 0            -6.47 bps  PASS
    C8 XPL 的**舊** G1 必須 > 3.0     3.93 bps  PASS

C7 只證明新關卡抓得到 XPL;**C8 才證明是這個改動抓到的**,而不是它本來就會
被別的關擋掉。一個只有 C7 沒有 C8 的反向證明是沒有分辨力的。

**Rule:** **一個判準的名字聽起來蓋到某件事,不代表它的算式蓋到了。**
凡是判準的名字是一個概念（「兩側性」「毒性」「流動性」）,要在它旁邊寫下
**它實際量的那個量**,並且問「這個概念還有沒有別的面向,是這個量看不到的」。

第二條,關於反向證明的分辨力:**一個新關卡的反向證明要有兩半** ——
(a) 它抓得到那個已知的壞例子;(b) **舊的關卡放行了那個例子**。
只有 (a) 的話,你不知道是新關卡起了作用,還是它本來就會被別的東西擋掉。

第三條:**任何「兩個東西的差」的判準,先問它有沒有把兩者之間的持續偏移
算進去。** 我們在 2026-09-13 才因為非同步取樣造出過假價差,而這次是反過來 ——
一個**真實**的持續偏移沒有被算進去,於是一個單向的市場看起來像雙向的。

## 2026-09-14: 同一天兩次,監控指著一個已經停掉的標的 —— 告警一直響,而它報的是我自己造成的狀態

**What happened:**

第一次:早上停掉 AERO,但 `hmm_watch.py --pair AERO` 的迴圈沒停。使用者整個
下午一直收到「引擎行程不在 / status.json 32 分鐘沒動」的 Discord 告警,
直到他說「這個訊息一直在跳」。

**第二次:晚上我停掉 XPL,又忘了停它的看護。** 使用者說「我看還是 halt」。

**Root cause:**

「停掉一個標的」在這個系統裡要動的東西不只一個,而**監控那一側沒有任何東西
會提醒你它被留下了**。引擎停了,看護還活著,於是它忠實地報告「引擎不在」——
那句話是對的,只是它描述的是我自己造成的狀態,不是一個需要處理的事件。

而代價比噪音大:**真的紅燈被埋在假的紅燈裡**。那一整個下午,新鮮度看板
（6 小時才跑一次,而且最後一次自己 exit 1）跟 scan_pull 的 31 次失敗都沒有
被看到,因為唯一在響的頻道報的是別的東西。

**Correct approach:**

停一個標的時,監控與被監控的要一起動。目前是手動的,而手動的東西我今天漏了
兩次 —— 所以真正的修法方向是讓看護**自己從 STOP 檔讀它該不該報**,
那還沒做（登記在下面）。

**Rule:** **一個「某某不在了」的告警,在你自己剛把它停掉的時候是噪音,
而噪音會把同一個頻道裡的真紅燈蓋掉。** 凡是停掉一個被監控的東西,
同一個動作要把監控一起處理 —— 而如果那需要記得,它就會被漏掉。

第二條,更一般,今天踩了三次:**加一個新機制時,要枚舉「誰會讀這個狀態」,
而不是「我打算讓誰讀」。** 今天的 STOP 檔我接了 .bat 與看門狗兩個讀者,
然後 `account_budget.py` 立刻對一個已經停掉的成員報 B3 紅（$120 vs 上限
$70,而實際在跑的只有 $60）—— **一個對不存在的曝險報紅的風控檢查,
會訓練人忽略它。** 這是 [[2026-09-11 一份資料兩個讀者只驗了一個]] 的第三次。

## 2026-09-14: 三次上線、三個標的、三種死法 —— 而三把尺全部偏向「讓候選看起來合格」

**What happened:**

一天之內把 HMM 上線三次（GMX -> MET -> FIL），每次都找到一個新的死因，
然後換一個標的。使用者叫停：「**你不能一直停一個換一個，現在問題找出來，
然後再看怎麼做**」。

停下來把三次並排，問題不在標的，在**判準**：

| 尺 | 寫的是 | 真相 | 後果 |
|---|---|---|---|
| G1 | 掛單腿半價差 >= **5.0** bps | 損益平衡是 **7.4**（HL 半價差 2.5 ＋ 費用 4.9） | **門檻本身低於損益平衡線** |
| G3 | 有成交的分鐘 >= 30% | 灰塵流每分鐘都有成交 | 主動選中 $0.27 的流量 |
| M3 | markout 相對**成交價** > −1 bps | 我們成交在 ask，基準是 **+半個價差** | 價差越寬越會誤判通過 |

**三把尺都偏同一個方向**，而它們挑的正好是寬價差市場 —— 於是每一個候選都
「合格」，然後上線才死。

**M3 那個最惡性,因為它有數字而且看起來很好：**

    MET 實測 mean_bps **+30.26**（n=95）-> M3 門檻 >-1，**PASS**
    而 Lighter 半價差中位 33.98
    真實漂移 = 30.26 - 33.98 = **-3.72 bps** -> **FAIL**
    自曝：-3.72 與 session 損益 -$0.18 同號

反向證明把它講得更清楚 —— 賣出後 mid 逆向跑 10 bps（明確被挑走）：

    舊讀數 **+28.19**（照樣 PASS）    新讀數 **-10.00**（正確）

**Root cause:**

**一個判準寫下來的時候,沒有人把「基準是多少」代進去算一次。**
「markout > -1 bps」聽起來像是在說「行情不要逆著走」,而它實際說的是
「行情逆著走的幅度不要超過我們賺到的半價差」—— 那是完全不同的一句話,
而且在寬價差市場上它幾乎恆真。

同族：[[2026-08-26 把判準寫成一條恆真的假門檻]]（CI 下緣 vs 上緣）、
[[2026-09-12 極大值 ÷ 平均值當判準]]。這次多一種形狀：
**判準的零點不在零。**

第二層,關於我的行為:**「換一個標的」是一個看起來像在前進的動作。**
每次換都有新證據、新分析、新 commit,所以三次都感覺像進展。
而真正的訊號在第一次就有了 —— MET 的成交側別是 **121:0**,
我當時把它當成次要細節寫在報告的第三段。

**Correct approach（已做）:**

1. **M3 同時算兩個讀數**,`vs_mid_bps` 才判決,`vs_fill_bps` 保留
   （X4 判準逐字是相對成交價,而被引用過的數字不可以悄悄消失）。
   兩者之差 = 我們賺到的半價差,自己也是一個讀數。
   引擎另外記**掛單腿**的 mid —— 它原本只記對沖腿的,拿錯會把兩所基差
   混進逆選擇裡。`tests/test_markout_baseline.py` 五關釘住,含
   「被挑走時舊讀數仍為正」那一關（把病本身留在測試裡當對照）。
2. **G1 改成淨值 > 3 bps**（半價差 − HL 半價差 − 費用）。
3. **新增 G4 切片 >= 對沖腿最小單、G5 吃單流少數側 >= 35%** ——
   這兩個解釋了 MET（切片 $0.27、吃單流 93.1% 單向）與 CHIP（$0.03、97.4%）,
   而 G3 對它們完全是瞎的。
4. 讀不到就印「**未量**」,不是通過。

**Rule:** **寫下任何判準之後,把「什麼都沒發生」代進去算一次 —— 那個值就是
它的零點,而它多半不在零。** markout 的零點是半價差、成交率的零點是掛單
存活時間、「有成交的分鐘」的零點是灰塵。判準寫在偏離零點的量上,才在量東西。

第二條,關於怎麼收斂：**同一條線連續換三次標的而每次都有新死因時,
停下來把三次的判準並排,不要看三個標的。** 三個不同的死因配同一組判準,
先驗上更可能是判準的問題,而不是三次都運氣不好。
（[[2026-07-22 同一個方向連續 2-3 輪不夠好,先問是不是技術類別的天花板]]
 的同一條,只是那次的載體是渲染技術,這次是篩選門檻。）

## 2026-09-14: 我停了引擎卻沒停註冊，看門狗把一個會送真單的策略拉回來跑了 2 小時 21 分 —— 而那行警告是我自己寫的

**What happened:**

12:52 我把 MET 的看門狗註冊解除註解（WAF 恢復）。13:05 為了處理一個卡住的
部位，我停掉 MET 的行程。**但沒有停註冊。**

看門狗每 5 分鐘比對一次簽章，比不到就用 .bat 拉起來。於是 13:05 之後它把
**一個會送真單的引擎**重新拉起來，而我以為它停著，接下來 2 小時 21 分都在
做別的事（診斷、換標的、寫設定、跑測試、commit）。

**是使用者說「MET的倉位還在」我才發現的。**

最刺眼的是：那行警告是我**當天中午自己寫進看門狗**的，就在那一列旁邊——

> 「要停掉它**不可以只靠殺行程** —— 這張表會把它拉回來。
>   停止的順序：先 `echo flat`，再把這一列註解掉，最後才殺行程。」

我寫了順序，然後跳過了中間那一步。

**Root cause:**

**「停止」在這個系統裡是兩個動作，而只有一個會立刻看到效果。**
殺行程當場可見（`Get-CimInstance` 回空，我確認過而且貼了「MET 已完全停止」）；
解除註冊沒有任何當下的回饋，它的效果要等五分鐘後的**不發生**才看得見。
所以「看起來停了」這個證據，剛好只覆蓋兩個動作裡的一個。

這跟 [[2026-08-26 「執行過了」的判準永遠是產物不是退出碼]] 同族，但方向相反：
那次是把退出碼當成做完了，這次是把**當下的靜止**當成持續的靜止。
**一個由外部排程維持的行程，它的「停止」要驗的是五分鐘後還停著。**

**代價（誠實列出來）:**

* 2 小時 21 分的**無人看管**真單交易。這是最嚴重的一項 —— 金額小是運氣，
  不是控制。max_net_base 11.5、max_daily_loss 10、M5 HALT 全程有效，
  但沒有人在看。
* 損益 **−$0.18**（HL −$0.8922 / Lighter +$0.7105），兩所最後都是平的。
* 我在這段期間對使用者講的兩句話是錯的，而錯的原因就是這件事本身：
  「HL 從來沒送過任何一張單」（12:53 為真，13:40 起就不是了）、
  「MET 的 HL 腿結構上碰不到」（13:40~14:17 它整張單對沖了四次）。
  **我用一個舊快照描述一個正在動的系統。**

**Correct approach（已做）:**

停止的三步寫死在兩個地方（`run_hmm_*.bat` 檔頭與看門狗那一列旁邊），
而且**順序有理由**：`flat` 要在引擎還活著時送（它需要簽章），
註解註冊要在殺行程**之前**（否則中間那五分鐘它會回來）。

而真正的修法不是「下次記得」——是**判準改成產物**：
停完之後要等超過一個看門狗週期（>5 分鐘）再確認一次行程還是不在。
當下的 `Get-CimInstance` 回空**不構成證據**。

**Rule:** **凡是被外部排程／看門狗維持著的東西，「我停了它」不是一個當下
可以驗證的命題。** 驗證它要跨過至少一個排程週期 —— 在那之前，
你手上只有「它現在不在」，而那跟「它會留在不在的狀態」是兩回事。

第二條，更一般：**講一個正在跑的系統的現況之前，先問那個數字是幾分鐘前的。**
我那句「HL 歷史成交 0 筆」在說出口時是對的，四十七分鐘後就不是了，
而我一直拿它當前提往下推論，還據此退役了一個標的。
任何被引用出去的狀態都要帶時間戳，而「現在」要重新查一次。

## 2026-09-14: shadow 跑了十小時全綠，而 live 會在啟動的第一秒 RuntimeError —— 因為 shadow 唯一不做的那件事，正好是唯一會擋住開機的那件事

**What happened:**

使用者問「確認現在情況跟下單的管線都有沒有通」。我去讀兩條腿的 `init_signer`，
確認「探一下」不會送出任何東西（HL 是建構 `HLAccount`；Lighter 是
`SignerClient(...)` + `check_client()`，兩個都不下單），然後順手查了套件：

    lighter                    已安裝
    hyperliquid-python-sdk     **沒有**

而 HL 的 `init_signer` 第一件事就是 import 它，import 不到就
`RuntimeError("live trading on Hyperliquid needs the official SDK")`。
**live 開不起來，而且是在第一秒。**

**十小時的 GMX shadow 對這件事零資訊量**，因為 shadow **刻意不呼叫
`init_signer()`** —— 那正是它保證「一張單都不送」的手段之一
（六個送出點裡有五個被 `_blocked()` 擋掉，第六個靠
`assert signer is not None`）。所以「shadow 很乾淨」跟「live 啟動得了嗎」
是兩個不相干的命題，而我一整天都把前者當成後者的旁證在報告。

**最刺眼的是 shadow 自己的檔頭，那段話是為了這件事寫的：**

> 「A rehearsal that cannot start is not a rehearsal, so shadow warns where
> live refuses -- because **finding that out at go-live is the failure this
> mode exists to prevent**.」

它已經照這句話做了三件事（風控區塊、設定完整性、憑證齊不齊），
**唯獨漏掉最會發生的那一個：套件沒裝。** 檔頭描述的是應然，
而應然讀起來像是已經做到了 —— 同族第三次，前兩次是
[[2026-09-11 在檔頭寫下判準不等於那個判準存在]] 與
[[2026-09-08 我在檔頭寫下這個病的名字，然後把同一個病留在那個檔案裡]]。

**Correct approach（已做，而且反向證明過）:**

shadow 啟動時也跑一次 `init_signer()`，失敗只 WARNING 不中止。
**只建構與驗證、不送任何東西**，所以 shadow 的不變式沒有動。
反向證明用的是真實條件不是注入 —— 先修好、SDK 還沒裝：

    [SHADOW] live would REFUSE to start — [HL] signer: ... needs the official SDK
    [SHADOW] [LIGHTER] signer would initialise OK

裝 `hyperliquid-python-sdk==0.24.0`（`--no-deps`，相依全部已滿足）之後：

    [HL] signer=0xA8fB... account=0x5777... (agent mode)
    [SHADOW] [HL] signer would initialise OK
    [SHADOW] [LIGHTER] signer would initialise OK

順手釘版（原本是 `>=0.9`，正是 [[2026-07-29 未釘版的 mcp]] 那個坑），
並在旁邊記下一個落差：這個 SDK 宣告 `websocket-client>=1.5.1` 而本機是
0.58.0 —— 我們只用它的簽章模組，而升級它會動到正在跑的 `lighter_tape`，
所以刻意不升，並把這件事寫在釘版的旁邊當作下次的第一嫌疑。

**Rule:** **一個「彩排模式」的價值，等於它跟正式演出**共用**的路徑有多長；
而它跳過的每一段，就是它結構上看不見的每一段。** 所以列出
「shadow 不做哪些事」這張清單，比列出「shadow 做了哪些事」有用得多 ——
清單上的每一項都是一個 live 專屬的失敗模式，而它們全部會在 go-live 那一秒
同時到齊。

第二條，具體到這次：**「相依套件裝了沒」是 live 專屬失敗模式裡最便宜也最常
發生的一個**，而它在任何 shadow / dry-run / paper 模式裡都測不到（那些模式
的存在理由就是不碰那條路徑）。判斷法很便宜：**把 live 才會走的那幾行
（建構簽章、讀憑證、連私有頻道）在 shadow 裡也跑一次，只是不送單。**

## 2026-09-14: 同一個判準我猜了兩次，兩次都跟引擎自己的行為對不上——而正確的做法是不要猜，去讀引擎寫的那個檔

**What happened:**

`hmm_screen.py` 的 G2 要回答「這個市場讓不讓引擎**兩側都報價**」。
我用錄製器的 `minutes.csv` 算它，連錯兩次：

| 版本 | 用什麼 | GMX 的買側 | 引擎實跑 |
|---|---|---|---|
| v1 | recorder 的 `sell_edge/buy_edge` | 0.0% | |
| v2 | 掛單–吃單構造 ＋ 設定的 thresholds | **34.1%** | |
| 真相 | 引擎自己的 `shadow.csv` | **1.8%** | **4,782 賣 : 6 買** |

**v1 錯在構造。** `recorder.py:13` 的定義是
`sell_edge = (entropy_bid / hedge_ask - 1)` —— **兩條腿都穿價差**，
那是 §0.75 的吃單–吃單。HMM 是掛單–吃單（在掛單腿的 ask 掛賣、
到吃單腿的 ask 吃單對沖）。在一個 91 bps 價差的市場上，兩者差一整個價差。

**v2 錯在別的地方，而我到現在也不知道是哪裡。** 定價、
`premium_persist_sec`、深度、post-only 都可能。

**而第二次之後我差點做的事才是真正的錯：繼續調到控制組變綠。**
C3（「GMX 必須過不了 G2」）連紅兩次，而每一次我都更接近
「把儀器擬合到我期待的答案」——那正是 C3 存在要擋的事。

**Root cause:**

我把「不要寫第二份實作」（mistake.md 2026-08-26）讀成
「拿現成的那個欄位」，而漏掉了前提：**那個欄位量的必須是同一件事。**
`sell_edge_mean_bps` 是現成的、是引擎那邊寫的、名字也對 ——
它只是在算另一個構造。

第二層：**一個判準連續猜不中的時候，問題不是「再猜一次」，
是「有沒有一個不會跟引擎不一致的來源」。** 而那個來源一直都在：
引擎跑 `--shadow` 時把**每一次報價決策**寫進 `shadow.csv`，含側別。
它不可能跟引擎不一致，因為它就是引擎寫的。

**Correct approach（已做）:**

G2 改成**只讀 `logs/<pair>/shadow.csv`**；沒跑過 shadow 就印「**未量**」，
而不是印 0 或當作通過。代價是 G2 需要先跑一輪 shadow（GMX 70 分鐘給了
4,788 次決策），換到的是「這個數字不可能跟決策者不一致」。

改完 C3 自己變綠了（GMX 98.2 : 1.8，不過 G2）—— **那是確認，不是動機**。

**Rule:** **凡是「引擎會不會做 X」的判準，先問引擎有沒有把它做過的事寫下來。**
自己從原始資料重算是在做第二份實作，而第二份實作在**構造**這一層出錯時
不會報錯 —— 它會給出一個看起來合理的數字。

第二條，關於控制組：**一個控制組連紅兩次，代表要換方法不是換參數。**
第一次紅可以是實作細節，第二次紅就是「這條路量不到那件事」。
繼續調的每一步都在把儀器擬合到答案上，而那是
[[2026-09-09 五項一致性檢查全部通過，真樣本外一驗就死]] 的同一個病
——只是那次擬合的是資料，這次擬合的是儀器。

第三條：**「未量」必須是一個可以印出來的值。** 把沒量過的東西印成 0，
就是把「不知道」寫成「知道而且是最壞的那個」；印成通過更糟。
這跟 [[2026-09-13 一支回答「錢夠不夠」的工具對一個有 $88.78 的帳戶報 $0.00]]
是同一條：未知狀態不可以長得像一個已知狀態。

## 2026-09-14: 我自己發明了一個判準，而它的方向是反的——它會把兩份設對的判成紅、把明天要上線的那份判成綠

**What happened:**

複製 `config_HMM_GMX.yaml` 開 MET 的設定時，`max_net_base: 2.0` 被原封帶過去。
那個值的**單位是基礎單位**，所以它隨價格縮放：

    GMX $7.80   ->  2.0 顆 = $15.60
    MET $0.234  ->  2.0 顆 = **$0.47**

看起來很清楚是個 bug，於是我寫了 `arblib/config_audit.py` 去掃全部設定，
判準寫成「容忍 < 0.5 張單 = **恆真**，一成交就踩線」。

跑出來 NBIS 與 NVDA_LL 紅（0.22 張單），GMX 綠（1.04 張單）。

**而那完全是反的。** 去讀程式碼才知道：

* `config.py:479` 的設計意圖白紙黑字：
  「tight enough that **a single stuck leg trips it**, loose enough that
  normal settle lag does not」
* `engine.py:1478`：`_maybe_hedge` 是在**報價結算之後**才檢查
  （註解：the only moment that matters after a partial fill），
  也就是立即對沖已經試過了

所以「對沖完全失敗」時 net 正好是**一張單**，而 `max_net_base` 必須**小於**
一張單才跳得起來。

| | 容忍張數 | 真正的判定 | 我的判定 |
|---|---|---|---|
| NBIS / NVDA_LL | 0.22 | **對的**（一條腿卡住就跳） | 紅 |
| **GMX** | **1.04** | **錯的（對沖全滅不會跳）** | **綠** |
| MET（我複製的） | 1.06 | 錯的 | 綠 |

**GMX 那份是幾小時前才在跑 shadow、準備翻 live 的那一份。**
我的稽核會告訴我它沒問題。

**Root cause:**

**我沒有去讀那個參數在程式碼裡被怎麼用，就發明了一個判準。**
判準是從「2.0 顆對 MET 只有 $0.47，太小了」這個正確的觀察外推的 ——
外推的方向是「太小會恆真」，而真相是這個閘門本來就該小。

這跟 [[2026-08-26 把判準寫成一條恆真的假門檻]] 是同一族，但更危險一級：
那次是判準沒有分辨力，這次是判準**有分辨力但指著相反的方向** ——
一個會把紅燈變綠的判準，比一個永遠紅的判準糟得多。

而救它的不是我的警覺，是**「兩份設定被判紅，而它們的註解自己說它們是對的」**
（NBIS 的原註解：`~$4.2 at 208 — a broken leg halts, dust does not`）。
兩台儀器對同一件事給出相反的答案時，先查它們跑在什麼之上
（mistake.md 2026-09-11），而這次「另一台儀器」是那行註解。

**連帶找到第二個同族的**：`net_tolerance_base` 也是基礎單位。
MET 在 HL 是 `szDecimals: 0` —— **最小交易單位是 1 整顆（$0.234）**，
所以兩腿的殘餘量子是 1 顆，而複製過來的 `0.01`（$0.0023）**永遠滿足不了**。

**Correct approach（已做）:**

判準從程式碼推，不從直覺推，而且把推導寫在判準旁邊：
`max_net_base` 必須 **< 1 張單**（否則對沖全滅不會跳）且 **> 3x 殘餘量子**
（否則粉塵誤觸）。全部數字從步長與張數算：

    GMX  2.0 -> 0.5 顆  = $3.90 = 0.26 張單 = 50 個量子
    MET  68  -> 16.0 顆 = $3.74 = 0.25 張單 = 16 個量子
    MET  net_tolerance_base 0.01 -> 2.0 顆（= 兩個量子）

**Rule:** **要為一個既有參數寫稽核之前，先去讀它在程式碼裡被怎麼用。**
一個從「這個數字看起來不對」外推出來的判準，有 50% 的機率指著反方向 ——
而它的錯法不是「沒抓到」，是「**把對的判成錯的、把錯的判成對的**」，
那會讓人去修本來是對的那幾份。

判斷法很便宜：`grep` 那個參數名，讀它被比較的那一行，以及**那個比較發生在
哪個時點**（這次的關鍵是「在立即對沖之後」，而那決定了 net 的量級是一張單
還是零）。

## 2026-09-13: 一支回答「錢夠不夠」的工具，對一個有 $88.78 的帳戶報了 $0.00 —— `or [{}]`，而我同一天才把這條寫進 commit 訊息

**What happened:**

`funding_status.py` 寫完三十分鐘後，對 Lighter 報：

    Lighter mainnet    永續權益 $0.00    現在能開 $0
    **還沒達標** —— 缺口：Lighter mainnet +$50.00

而同一分鐘直接打同一個端點：`total_asset_value: 88.780001`。**錢一直在。**

根因是這一行：

```python
acct = (lighter_get(...).get("accounts") or [{}])[0]
```

`lighter_get` 只檢查 `content-type` 是不是 JSON。**Lighter 被限流時的錯誤體
也是 JSON**，於是它通過了，`accounts` 不存在 -> `or [{}]` -> `acct = {}` ->
`total_asset_value` 缺 -> `float(None or 0)` -> **$0.00**。

沒有例外、沒有警告，輸出一列格式完全正常的 $0.00。

**Root cause:**

跟 [[2026-09-11 family_specs 的 `or {}` + continue]] **完全同一行程式碼形狀**，
而我在**同一天**的 commit 訊息裡引用過那一條（「空輸出必須 raise，不可以回空
容器」）。差別只在後果的類別，而這次的類別更糟：

* 那次是**一份判決檔安靜地停在六天前** —— 錯的方向是「沿用舊數字」。
* 這次是**一個關於錢的工具報零** —— 錯的方向是「你沒有錢」。

**一個回答「錢夠不夠」的工具報零，會讓人去搬錢。** 我當下的第一個念頭確實是
「Lighter 的錢不見了」，而使用者剛好在二十分鐘前才動過兩個帳戶 —— 如果我把
那句話講出去，他很可能會去查、去轉、甚至去補一次。**假的資金短缺警報會造成
真的資金移動。**

擋下它的是老規矩：**數字跟二十分鐘前差一個量級就先查儀器**。二十分鐘前同一支
工具印過 $88.78。

**Correct approach（已修）:**

1. `accounts` 為空 -> **raise，並把回傳的 JSON 前 200 字印出來**（限流的錯誤體
   長什麼樣，下次一眼就知道）。`orderBookDetails` 回 0 個市場同樣 raise。
   理由寫在原地，包含這次的數字。
2. 讀不到的場館**進 `unread` 清單**，不進「每腿上限」的 `min()`，而且輸出明說
   「下面的上限只算了讀得到的那些，**是上界不是結論**」。
   少印一列會被讀成「那一邊沒問題」，補一個 0 會被讀成「那一邊沒錢」——
   兩個都不行，唯一對的是**說出來**。

**Rule:** **凡是輸出會影響「要不要搬錢」的程式，它的未知狀態必須是「不知道」，
不可以是 0。** 金額的 0 跟「讀不到」在版面上長得一模一樣，而它們要求的下一個
動作相反（0 -> 去補錢；讀不到 -> 重跑一次）。

第二條，關於 `or {}` / `or []` 這個形狀：**它保護的是「這一筆沒有」，
它不該保護「整個回應沒有」。** 判斷法很便宜：**這個容器有沒有可能合法地是空的？**
帳戶索引是我們自己填的、市場表有 234 筆 —— 兩個都不可能合法為空，所以兩個都該 raise。

第三條，關於「同一天第二次」：這是今天第二次踩 `or {}`，也是今天第五次把反斜線
穿過 heredoc（這次是 `print("\n...")` 變成 `print("` + 真換行，被 `py_compile`
抓到）。[[2026-09-13 處方寫著寫成獨立 .py 檔]] 那一條的結論
「**同一個形狀在一個 session 裡出現第二次，就停下來換做法，不要在原地修第二次**」
我今天寫了、也沒照做。所以把它升級成一條可執行的：
**這個 session 已經犯過的形狀，下一次動手前先問「我正在做的事是不是那個形狀」**
—— 含反斜線的內容一律用 Write/Edit，不要經過任何 shell。

## 2026-09-13: 我在開機啟動器裡加了兩行中文註解，cmd.exe 就少跑了六行 —— 退出碼 0，而那六行是六支錄製器

**What happened:**

掃描器搬到 Railway 之後，要把開機啟動器（Startup 的
`entropy-arb-record.bat`）裡那一行 `start ... run_scanner.bat` 停掉。
我照規矩用 bytes 寫回、保行尾、加了兩行**中文 REM** 說明為什麼。

然後照 [[2026-08-19 改完 .bat 必須立刻執行一次]] 做驗收 —— 但這支不能真的
執行（它會再開九支已經在跑的錄製器），所以我改成：複製一份、把 `start`
換成 `echo`、跑那一份。**同一個解析器、同一份內容、沒有副作用。**

跑出來 **只有 3 行**，而檔案裡有 9 行 `start`。**而 exit code 是 0。**

四個變體隔離：

| 變體 | 實際跑到的 `start` 行數 |
|---|---|
| A 現況（含中文 REM） | **3** |
| B 中文 REM 換成 ASCII | 9 |
| C 拿掉那兩行 REM | 9 |
| D 拿掉全部 REM | 9 |

**就是那兩行中文。**

**Root cause:**

cmd.exe 逐行讀 .bat 的時候是用**位元組偏移**在記位置（它會重新開檔、
seek 到上一次的位置），而它用 **OEM 碼頁**（這台是 cp950）解讀那些位元組。
檔案裡出現 UTF-8 的多位元組序列時，那個記帳就歪掉 —— 於是它 seek 到一個
錯的位置，跳過中間那幾行，然後從某個地方繼續。

**而失效方向是最壞的那個**：不報錯、不中止、退出碼 0，只是**少做幾件事**。
這是這個專案最熟悉的形狀（行程活著、功能死了），只是載體換成了行尾與碼頁。

**全掃之後，規律很乾淨，而它不是「不要用中文」：**

| 檔 | 非 ASCII | 行尾 | 結果 |
|---|---|---|---|
| `run_hmm_GMX.bat` | 132 位元組 | **CRLF** | **OK** |
| `run_recorder_universe.bat` | 119 位元組 | **CRLF** | **OK** |
| `entropy-arb-record.bat`（我改的） | 有 | **LF-only** | **跳 6 行** |
| `start_engine.bat` | 33 位元組 | **LF-only** | **跳 1 行** |

**UTF-8 在 CRLF 的 .bat 上沒事，在 LF-only 的 .bat 上會跳行。**
所以這條跟 [[2026-08-19 Edit 把 CRLF 換成 LF]] 是同一個根的兩個症狀：
那次 LF-only 讓整支失效，這次 LF-only + UTF-8 讓它**部分**失效。
部分失效更難發現，因為它看起來像成功。

**順手抓到一個既有的**：`start_engine.bat`（Startup、舊線 sweep-failure
的 paper 引擎）第 1 行有中文 REM、LF-only，於是**第 2 行 `set TG_TOKEN=`
被跳過** —— 那支引擎的 Telegram 告警一直是啞的。目前沒釀災，因為
`live_engine.py` 根本沒在跑（舊線 2026-09-07 結案）。它是地雷不是損失。

**第二層，而且我今天犯了兩次同一件事：我的稽核工具自己壞了。**

第一版稽核把原始指令的前 40 個字元接在 `echo RAN ` 後面，於是
`timeout /t 30 /nobreak >nul` 那一行的 **`>nul` 也被 echo 出去** ——
輸出被丟到 nul，看起來像「這行沒跑」。結果**每一支純 ASCII 的 .bat 也報
「少跑 1 行」**，而那正是它壞掉的證據：純 ASCII 的檔應該全跑。

救它的是 `factor-research.md` 最後一條：**自己剛寫的儀器要先在一個答案已知
的資料上跑一次**。這裡答案已知的對照組就是那九支純 ASCII 的 `run_recorder_*`
—— 它們一起報錯，所以錯的是尺不是被量的東西。同族第 N 次：
[[2026-07-29 自己寫的診斷有 bug]]、[[2026-08-26 反向證明沒有變紅先懷疑破壞注入]]。

**Correct approach（已做）:**

`.bat` 的註解一律 **ASCII**，並在註解裡寫明為什麼（那行註解自己就是證據）。
`entropy-arb-record.bat` 換成 ASCII 之後重驗：**9 支全在、掃描器不在**。

驗收方式本身也值得留下 —— **「改完 .bat 必須立刻執行一次」在有副作用的
啟動器上要改寫成**：複製一份、把會產生副作用的指令（`start` / `python` /
`timeout` / `goto`）換成一個**不帶原文**的標記（`echo RAN <行號>`），
跑那一份，數行數。不帶原文這件事是必要的：帶原文就會把 `>nul` 一起帶進去。

**Rule:** **`.bat` 的註解只能用 ASCII。** UTF-8 的多位元組序列會打亂
cmd.exe 的位元組偏移記帳，讓它**跳過幾行然後正常結束** —— CRLF 的檔僥倖
沒事，LF-only 的檔會中。判斷法很便宜而且是二元的：
`任何非 ASCII 位元組 ∧ 沒有 CRLF` = 這支 .bat 現在就在跳行。

第二條，關於驗收：**一支不能直接執行的腳本，不代表它不用驗** ——
把副作用中性化之後跑同一個解析器就好。而中性化的替身**不可以夾帶原文**，
因為原文裡的重導向會把你的證據吞掉。

**Correct approach:**

開任何新的**執行**工作之前，先在**所有相關的 repo** 裡 grep 既有引擎的
模式旗標（`mode`、`maker`、`HEDGE_VENUES`、`_make_venue` 這類），
把「我們能跑什麼」列成一張表，再拿新線的需求去對。
今天實際有效的三個 grep 一共花不到兩分鐘：

    grep -rn "HEDGE_VENUES"        -> 可對沖的場館只有三個
    grep -rn "maker_venue"         -> 掛單腿是可設定的
    grep -n "_make_venue" engine.py -> 兩條腿都可以是 Lighter

**Rule:** **「這是一條新線」不蘊含「執行層是新的」。**
一條策略線的新東西幾乎總是**判斷層**（選什麼、多寬、多大）；
執行層（送單、撤單、對沖、對帳）在同一個場館上是同一件事，
而它是最貴、最危險、也最不該有第二份的那一層。
判斷法很便宜：**先問「如果這個判斷是對的，哪一支現有程式會收到它？」**
——答不出來才是真的要寫新的。

第二條，關於 repo 邊界：**把一條線搬到另一個 repo，會讓「我們已經有什麼」
這個問題在新 session 裡默默變成不可見。** 搬家時留下的那座橋
（`research/arb_home.py`）解決的是「程式怎麼找到它」，沒有解決
「人怎麼知道它有什麼」。凡是跨 repo 的能力，**要在會被讀到的那一側
寫下一行「這件事在那邊已經有了」**——這次該寫在 flow_system 的 TODO
§1.40 開線那一節，而它沒有。
